# Acceptance Criteria Table
Traditional Chinese Music AI Music Generation System - Acceptance Criteria Table (v1.1)

| No. | Scenario Type | Test Scenario | Evaluation Metric | Threshold + Tolerance | Measurement Method | Failure Handling Measures |
|-----|---------------|---------------|-------------------|----------------------|---------------------|---------------------------|
| 1 | Normal Scenario | User inputs valid emotions, styles, and keywords to generate music normally | Generation Success Rate | 100%, tolerance 0% | Initiate a normal request and check that the returned status=success | Check the model service and input parsing logic, then regenerate |
| 2 | Normal Scenario | Generated MIDI is playable, and sheet music images are accessible | Output Usability | 100% available, tolerance 0% | Download and play MIDI, open image links | Check the file storage service and regenerate output files |
| 3 | Boundary Scenario | User inputs only 1 keyword with other parameters as default | Input Compatibility | Generate normally without errors | Submit the minimum valid input and observe system behavior | Optimize the input default value logic to ensure stability for boundary inputs |
| 4 | Boundary Scenario | User sets music duration to 60 seconds (maximum value) | Duration Accuracy | Actual generated duration = 60 seconds, tolerance ±1 second | Check the output duration_sec field | Limit the maximum duration and fix the model generation logic |
| 5 | Boundary Scenario | User exceeds the per‑minute request limit (50 requests/min) | Rate Limiting Effectiveness | Return 429 status code after 51st request in the same minute | Send 51 requests within a 60‑second window; verify the 51st is rejected | Optimize rate limiting logic to ensure accurate token bucket or sliding window |
| 6 | Degradation Scenario | Generation latency >3s triggers degradation | Degradation Success Rate | 100% return degraded music, tolerance 0% | Simulate a network/processing delay ≥3s and check that status=degraded | Optimize timeout judgment and fallback logic |
| 7 | Degradation Scenario | User inputs ambiguous emotions (both cheerful and sad) | Automatic Processing Accuracy | ≥ 95% automatic selection of calm emotion | Submit ambiguous emotions and check the output emotion_detected field | Optimize emotion parsing rules; if accuracy falls below 95%, add manual‑override fallback |
| 8 | Negative Scenario | User submits empty input (no emotion, style, or keyword) | Parameter Validation | Reject directly and return 400 error | Submit an empty request and check the error code | Strengthen front‑end/input validation to block empty requests |
| 9 | Negative Scenario | User inputs invalid keywords (abc123, special symbols) | Keyword Filtering | Ignore invalid words without affecting generation | Submit invalid keywords and check if generation proceeds normally | Optimize keyword cleaning logic to filter illegal characters |
| 10 | Negative Scenario | User sends high‑frequency requests, triggering per‑minute rate limiting | Rate Limiting Rules | Return 429 status code for each request after the 50th within a sliding 60‑second window | Send 6 requests within 1 second; verify at most 1 is accepted before rate limiting kicks in | Adjust rate limiting thresholds and implement token‑bucket with per‑user counters |
| 11 | Boundary Scenario | Generate an 8‑bar phrase under concurrent load (50 users, 30 seconds) | Latency | p95 ≤ 2.2s, tolerance 0.1s | Use k6 to run 50 virtual users for 30 seconds, record end‑to‑end latency per request, compute p95 | Optimize model inference pipeline or add caching for popular patterns |
